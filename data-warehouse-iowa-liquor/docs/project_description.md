# Project Description

## Project Title

Hurtownia danych do analizy sprzedazy, produktow, sklepow i regionow na podstawie danych Iowa Liquor Sales

## What project is

This project is student data warehouse for analysis of retail sales and distribution of regulated products. It uses public Iowa Liquor Sales dataset as real business-like source. Goal is not consumption analysis. Goal is sales, margin, product, vendor, store, and regional performance analysis.

Project is built with simple teaching-oriented architecture:

```text
Socrata CSV API
-> Apache Airflow
-> raw CSV files
-> SQL Server staging
-> SQL Server dimensional warehouse
-> SQL semantic views
-> Streamlit dashboard
```

It is designed to be:

- easy to explain during university presentation,
- based on real public data,
- runnable on normal laptop,
- maintainable without enterprise complexity,
- complete enough to show full data warehouse flow from source to reports.

## Why this topic

This topic fits data warehouse course well because dataset has many natural analysis dimensions:

- time,
- store,
- geography,
- product,
- category,
- vendor,
- packaging.

It also has business measures that are good for dimensional modeling:

- sales value,
- bottles sold,
- volume sold,
- margin.

Because source data is public and large enough, project can show real ETL, real modeling decisions, real quality checks, and real reports. That makes project stronger than synthetic example.

## Why Iowa Liquor Sales dataset

Dataset is good for student warehouse because:

1. It is real online data.
2. It is available through API, so ETL can run live.
3. It contains transaction-level rows, which is ideal for fact table grain.
4. It already includes rich descriptive attributes for stores, products, vendors, and geography.
5. It supports multiple business questions without needing many external sources.

Source:

```text
https://data.iowa.gov/resource/m3tr-qhgy.csv
```

## Business problem

Organization wants to understand how retail distribution performs across time, products, vendors, stores, and regions.

Questions include:

- which categories generate highest revenue,
- which products sell best by quantity,
- which stores and counties generate strongest sales,
- which vendors have biggest share,
- where volume is high but revenue is weaker,
- how sales structure changes over time,
- what margin is generated by product groups and vendors.

This is classic analytical problem. Transaction system is not enough because decision makers need aggregated, consistent, reporting-friendly structure.

## Why data warehouse needed

Raw source data is useful for extraction, but weak for reporting directly.

Problems with raw source:

- source columns are not standardized for reporting,
- same analytical logic would be repeated in every report,
- business users should not query raw operational structure,
- joins, aggregations, and calculated metrics would be duplicated,
- performance and consistency become harder.

Warehouse solves this by:

- storing cleaned staging data,
- loading dimensional model,
- defining reusable semantic SQL views,
- exposing stable reporting layer for dashboard.

## How architecture works

### 1. Extract

Apache Airflow calls Socrata CSV API with date filters and pagination.

Example:

```text
https://data.iowa.gov/resource/m3tr-qhgy.csv?$where=date between '2023-01-01T00:00:00' and '2023-12-31T23:59:59'&$limit=50000&$offset=0
```

Data is downloaded page by page and saved as raw CSV files.

Why raw files are kept:

- reproducibility,
- easier debugging,
- easier presentation,
- clear separation between extract and load stages.

What is extracted:

- transaction rows from Iowa Liquor Sales source,
- only fields needed for store, product, category, vendor, packaging, time, and measures,
- only chosen date range required for project run.

Why this extraction approach:

- source is online and public,
- ETL can be shown live,
- pagination makes large source manageable,
- saved files create auditable raw layer.

### 2. Staging

Raw files are loaded into `stg.iowa_liquor_sales_raw`.

At this step project:

- normalizes column names,
- converts date and numeric values,
- keeps source-like structure,
- preserves source rows,
- creates technical row hash.

Why staging exists:

- protects warehouse from direct source format changes,
- gives place for controlled cleaning,
- allows quality checks before dimensional load.

How staging works in this project:

- source API output is loaded into `stg.iowa_liquor_sales_raw`,
- data is still close to source structure,
- cleaning is limited to what is needed before warehouse load,
- source rows are preserved for traceability.

### 3. Dimensional model

Warehouse schema `dw` contains:

- `fact_sales`
- `dim_date`
- `dim_store`
- `dim_product`
- `dim_category`
- `dim_vendor`
- `dim_packaging`

Fact grain:

One row in `dw.fact_sales` represents one sales line of one product in one store, on one invoice, on one day.

Why star schema:

- easy to explain,
- easy to query,
- good for BI tools,
- supports aggregation by many dimensions,
- fits university dimensional modeling requirements.

### 4. Semantic layer

Schema `sem` contains reporting views such as:

- `vw_sales_by_month`
- `vw_sales_by_category`
- `vw_sales_by_store`
- `vw_sales_by_vendor`
- `vw_sales_by_geography`
- `vw_top_products`
- `vw_margin_analysis`
- `vw_volume_vs_revenue`
- `vw_kpi_summary`

Why semantic layer exists:

- keeps report logic in one place,
- makes dashboard simpler,
- avoids querying raw fact and dimensions directly,
- improves consistency across reports.

How semantic layer works:

- SQL views expose business-friendly structures,
- technical joins are hidden,
- dashboard reads only from `sem`,
- measures and aggregations are reusable across reports.

### 5. Reporting

Streamlit reads only from semantic views.

Why Streamlit:

- lightweight,
- easy to demo,
- simple Python stack,
- enough for interactive course project dashboard,
- no extra enterprise BI platform required.

## Important modeling decisions

### Geography in store dimension

Geography was kept in `dim_store`, not duplicated in separate `dim_geography`.

Why:

- cleaner star schema,
- less redundancy,
- closer to classic dimensional teaching examples,
- easier explanation.

### Packaging as sixth dimension

Project uses `dim_packaging` with:

- `pack`
- `bottle_volume_ml`
- `volume_group`

Why:

- avoids duplicate geography dimension,
- gives useful extra analytical slice,
- keeps minimum six dimensions requirement satisfied.

### Unit prices kept but treated correctly

`state_bottle_cost` and `state_bottle_retail` are stored in fact, but documented as non-additive unit measures.

Why:

- still useful for margin analysis,
- but they should be averaged, not summed.

### Negative source rows

Rows with negative measures remain in staging, but are excluded from fact table.

Why:

- raw source stays preserved,
- reporting fact remains consistent with sanity-check requirement,
- exclusion is visible in quality checks.

## Quality and validation

Project includes checks for:

- staging row count,
- fact row count,
- null foreign keys,
- negative fact measures,
- duplicate natural keys,
- fact-to-dimension join failures,
- difference between eligible staging sales and fact sales.

Why this matters:

- shows ETL is not black box,
- makes project more defensible during evaluation,
- demonstrates engineering discipline.
