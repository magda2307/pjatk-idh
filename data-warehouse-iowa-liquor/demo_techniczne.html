Projekt obejmuje przepływ danych: publiczny zbiór Iowa Liquor Sales, ekstrakcję do plików CSV, staging w SQL Server, model gwiazdy, widoki semantyczne oraz raporty analityczne w Streamlit.

  • Źródło danych: publiczny, niegenerowany zbiór Iowa Liquor Sales.
  • Orkiestracja: Apache Airflow, DAG iowa_liquor_etl.
  • Hurtownia: SQL Server, schematy stg, dw, sem.
  • Raportowanie: Streamlit oparty o widoki semantyczne.

Źródło danych

Źródłem danych jest zbiór Iowa Liquor Sales. Implementacja zawiera mechanizm buforowania plików lokalnie w celu zapewnienia stabilności.

Konfiguracja ekstrakcji

  • Endpoint CSV: https://data.iowa.gov/resource/m3tr-qhgy.csv
  • Domyślny zakres: 2023-01-01 do 2023-12-31
  • Domyślny limit strony: SOCRATA_LIMIT=50000
  • Filtr API: date between ..., paginacja przez $limit i $offset
  • Sortowanie pobrania: date, invoice_line_no

Zakres dostępny w API

  • Format dat w Airflow i API: YYYY-MM-DD, np. 2023-01-01.
  • Opis katalogowy Iowa Liquor Sales podaje zakres od 2012-01-01 do danych bieżących.
  • W katalogu Data.gov metadane zbioru były aktualizowane 2026-04-04, a dane ostatnio modyfikowane 2026-04-01.
  • API Socrata filtruje dane po polu date, więc zakres podaje się jako start_date i end_date.
  • Wybrany zakres do prezentacji obejmuje rok 2023: od 2023-01-01 do 2023-12-31.
  • Do krótkiego testu można zawęzić zakres, np. 2023-01-01 do 2023-01-31.

Dane w projekcie

Źródłem jest publiczny zbiór Iowa Liquor Sales. Jeden wiersz źródłowy opisuje jedną linię sprzedaży produktu: kiedy sprzedano produkt, w którym sklepie, jaki produkt i kategorię, od jakiego vendora, w jakim opakowaniu oraz za jaką wartość.

Obszar danych Przykładowe pola źródłowe Jak projekt ich używa
Identyfikacja sprzedaży invoice_line_no, date Tworzy numer faktury/linii i klucz daty. To podstawa ziarna tabeli faktów.
Sklep i lokalizacja store, name, address, city, county, zipcode, store_location Zasila dw.dim_store. Miasto, county i współrzędne są używane w raportach geograficznych i mapie.
Produkt i kategoria itemno, im_desc, category, category_name Zasila dw.dim_product i dw.dim_category. Te pola odpowiadają za rankingi produktów i kategorii.
Vendor vendor_no, vendor_name Zasila dw.dim_vendor. Raport pokazuje udział vendorów w sprzedaży i marży.
Opakowanie pack, bottle_volume_ml Zasila dw.dim_packaging. Projekt grupuje pojemności jako small, standard, large i extra_large.
Miary sprzedaży state_bottle_cost, state_bottle_retail, sale_bottles, sale_dollars, sale_liters, sale_gallons Zasila dw.fact_sales. Projekt liczy sprzedaż, wolumen, liczbę butelek i marżę.

Inżynieria cech i czyszczenie danych

Podjęte decyzje dotyczące transformacji danych obejmują dostosowanie formatów do wymagań typów bazodanowych oraz utworzenie dodatkowych atrybutów analitycznych dla modelu wielowymiarowego.

1. Czyszczenie wartości finansowych

Pole źródłowe: state_bottle_cost, sale_dollars
Wartość surowa: "$1,234.56"
Po transformacji: 1234.56 (Typ: DECIMAL)

Usunięcie symboli walut i separatorów tysięcy za pomocą metod na ciągach znaków w Pythonie. Skrypt wymusza rzutowanie na typ numeryczny przed wczytaniem danych do SQL Server.

2. Wyodrębnianie współrzędnych

Pole źródłowe: store_location
Wartość surowa: "POINT (-91.530463 41.666324)"
Po transformacji: latitude: 41.666324, longitude: -91.530463 (Typ: FLOAT)

Zastosowanie wyrażeń regularnych do wyodrębnienia szerokości i długości geograficznej z formatu przestrzennego WKT.

3. Wzbogacenie wymiaru daty

Pole źródłowe: date
Wartość surowa: "2023-11-25"
Po transformacji: year: 2023, month: 11, quarter: 4, is_weekend: 1, day_name_pl: 'Sobota'

Rozbicie daty na komponenty oraz dodanie znacznika typu dnia (weekend) w celu usprawnienia agregacji.

4. Kategoryzacja pojemności (Bucketing)

Pole źródłowe: bottle_volume_ml
Wartość surowa: 750, 1750, 50
Po transformacji: volume_group -> "standard", "large", "small"

Grupowanie ciągłych wartości pojemności do dyskretnych przedziałów analitycznych.

5. Wyliczanie miar pochodnych

Pola źródłowe: state_bottle_retail, state_bottle_cost, bottles_sold
Logika: (Retail - Cost) * Bottles
Po transformacji: Nowa miara: margin_amount

Kalkulacja marży kwotowej na poziomie wiersza w celu uproszczenia zapytań agregujących.

6. Obsługa braków danych (Imputacja)

Pole źródłowe: category_name, store_number
Wartość surowa: NULL, NaN, puste ""
Po transformacji: "UNKNOWN"

Przypisanie wartości domyślnej "UNKNOWN" dla brakujących danych przy użyciu funkcji COALESCE.

Silver

Warstwa Silver to tabela stg.iowa_liquor_sales_raw zasilana relacją 1:1 z plików CSV.

Proces obejmuje typowanie danych przed masowym wstawieniem za pomocą pyodbc.fast_executemany.

Architektura:
  • Unifikacja danych: Puste wartości mapowane są na obiekt None.
  • CDC: Generowanie hasha source_row_hash dla wiersza.
src/load/sqlserver_loader.py (Masowy insert)
def insert_dataframe_to_staging(df: pd.DataFrame, batch_size: int = 5000) -> None:
    insert_sql = f"INSERT INTO stg.iowa_liquor_sales_raw ({columns}) VALUES ({placeholders})"
    rows = [tuple(row) for row in df.itertuples(index=False, name=None)]
    
    with sqlserver_connection() as connection:
        cursor = connection.cursor()
        cursor.fast_executemany = True
        for start in range(0, len(rows), batch_size):
            cursor.executemany(insert_sql, rows[start : start + batch_size])
Gold

Warstwa Gold zawiera model gwiazdy w schemacie dw oraz widoki semantyczne w schemacie sem.

Procesy ładowania wykorzystują deduplikację danych oraz obsługę brakujących kluczy biznesowych przy użyciu COALESCE.

Architektura:
  • Reset tożsamości: Wykorzystanie DBCC CHECKIDENT przy pełnym odświeżaniu danych.
  • Integralność: Asercje weryfikujące poprawność powiązań kluczy.
src/transform/warehouse_transform.py (Deduplikacja)
WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY COALESCE(NULLIF(store_number, ''), 'UNKNOWN')
               ORDER BY date DESC, staging_key DESC
           ) AS rn
    FROM stg.iowa_liquor_sales_raw
)
INSERT INTO dw.dim_store (...)
SELECT ... FROM ranked WHERE rn = 1;

Warstwa semantyczna i logika biznesowa

Schemat sem wydziela logikę biznesową od fizycznej bazy. Stosuje zasadę Single Source of Truth dla spójności raportowania.

Bezpieczeństwo
dzielenia
(Division by Zero)

Zastosowanie NULLIF w obliczeniach zapobiega przerwaniu zapytań przez błędy dzielenia przez zero, zamieniając wynik na NULL.

sql/04_create_semantic_views.sql (sem.vw_kpi_summary) 
SELECT
    SUM(f.sale_dollars) / NULLIF(COUNT(DISTINCT f.invoice_number), 0) AS avg_invoice_value,
    CAST(100.0 * SUM(f.margin_amount) / NULLIF(SUM(f.sale_dollars), 0) AS DECIMAL(9,2)) AS avg_margin_percent
FROM dw.fact_sales f;
Kalkulacja
udziału w rynku
(Market Share)

Wykorzystanie CTE do wyizolowania sumy całkowitej w połączeniu z CROSS JOIN w celu obliczenia udziału procentowego kategorii.

sql/04_create_semantic_views.sql (sem.vw_sales_by_category) 
WITH totals AS (
    SELECT SUM(sale_dollars) AS all_sales FROM dw.fact_sales
)
SELECT
    c.category_name,
    CAST(100.0 * SUM(f.sale_dollars) / NULLIF(MAX(t.all_sales), 0) AS DECIMAL(9,2)) AS sales_share_percent
FROM dw.fact_sales f
CROSS JOIN totals t
GROUP BY c.category_name;
Problem średniej
ze średnich
(Podwójne grupowanie)

Kaskadowa agregacja wykorzystująca CTE do podsumowania obrotów sklepu przed uśrednieniem wyniku w wymiarze geograficznym.

sql/04_create_semantic_views.sql (sem.vw_avg_sales_per_store_by_month_region) 
WITH monthly_store_sales AS (
    SELECT d.year, d.month, s.city, s.store_key, SUM(f.sale_dollars) AS store_month_sales
    FROM dw.fact_sales f
    JOIN dw.dim_date d ON d.date_key = f.date_key
    JOIN dw.dim_store s ON s.store_key = f.store_key
    GROUP BY d.year, d.month, s.city, s.store_key
)
SELECT year, month, city, AVG(store_month_sales) AS avg_sales_per_store
FROM monthly_store_sales
GROUP BY year, month, city;

Szczegółowy kod ETL: Przewodnik Krok po Kroku

Ten rozdział to dokładna dokumentacja "linijka po linijce", która wyjaśnia, co dokładnie dzieje się w kodzie podczas uruchamiania procesu ETL w tym projekcie.

KROK 1: Ekstrakcja (Extract)

Główny plik: src/extract/socrata_extract.py

  • Konfiguracja: Ustalane są ramy czasowe. Domyślnie projekt przetwarza rok 2023-01-01 do 2023-12-31. Kod waliduje, by data początkowa nie była późniejsza niż końcowa.
  • Pobieranie w pętli: Łączymy się z endpointem REST API przez bibliotekę requests. Używamy paginacji: $limit i $offset. Z każdym przebiegiem zapisywana jest "strona" (np. part_000.csv).
  • Mechanizm Fallback Cache: Jeśli API Socrata zwróci błąd, kod w bloku except requests.RequestException: przechwytuje wyjątek. Sięga po zrzucone wcześniej pliki zapisane lokalnie, filtruje po polu daty, po czym przepisuje je jako udany plik ekstrakcji. Proces jest 100% niezależny od serwera, NIE GENERUJĄC sztucznych danych.

KROK 2: Obiekty SQL

Pliki: 01_create_schemas.sql, 02_create_staging_tables.sql, 03_create_dw_tables.sql

  • Staging: Tworzona jest wysoce tolerancyjna na błędy tabela, głownie typy NVARCHAR lub DECIMAL. Otrzymuje pole staging_key BIGINT IDENTITY(1,1).
  • Tabele DW: Skrypt wpierw zdejmuje relacje ALTER TABLE dw.fact_sales DROP CONSTRAINT ..., a potem robi DROP TABLE zapewniając czysty Full Refresh.
  • Każdy wymiar używa klucza syntetycznego IDENTITY(1,1) NOT NULL PRIMARY KEY.
  • Tworzona jest dw.fact_sales i odtwarzane są powiązania FOREIGN KEY.

KROK 3: Ładowanie do Stagingu

Główny plik: src/load/sqlserver_loader.py

  • normalize_column_name poprawia nazwy kolumn źródłowych w snake_case.
  • parse_location_value czyta geolokalizator POINT (-93 42) i wyciąga z tego dokładne floaty dla latitude i longitude.
  • clean_money_or_number fizycznie usuwa w Pythonie znaki $ i przecinki by SQL w ogóle mógł przyjąć to do typu DECIMAL. Następnie pd.to_numeric(errors="coerce").
  • Suma kontrolna: build_row_hash łączy fakturę, datę i numer sklepu dając stały hash przy użyciu SHA-256.
  • Wrzut przez pandas w paczkach po 5000 sztuk. Przed wkładem uruchamiane jest TRUNCATE TABLE.

KROK 4: Ładowanie Wymiarów

Wywołanie: warehouse_transform.py -> load_dimensions()

  • Przed wkładem uruchamiane jest DBCC CHECKIDENT ('dw.[tabela]', RESEED, 0);.
  • dim_date: SQLowa funkcja FORMAT(), DATEPART() wyciąga dane z daty. Konstrukcja z CASE buduje flagę is_weekend.
  • Rozwiązanie duplikatów: Projekt używa CTE wraz z funkcją okna:
    ROW_NUMBER() OVER (PARTITION BY [Klucz] ORDER BY date DESC, staging_key DESC).
    Bierzemy wyłącznie pierwszy rekord po dacie i zapisujemy go raz do wymiaru.
  • dim_packaging: Logika CASE WHEN grupuje pojemności na koszyki ('small', 'standard' itd).

KROK 5: Ładowanie Faktu Sprzedaży

Wywołanie: warehouse_transform.py -> load_fact_sales()

  • Łączymy Staging jako instancję prawdy poprzez naturalne wartości kluczy na wygenerowane klucze syntetyczne w wymiarach (np. JOIN dw.dim_store s ON s.store_number = raw.store_number).
  • Pola liczbowe zabezpieczane są za pomocą COALESCE(zmienna, 0).
  • Wyliczenie marży w locie:
    (COALESCE(raw.state_bottle_retail, 0) - COALESCE(raw.state_bottle_cost, 0)) * COALESCE(raw.bottles_sold, 0) AS margin_amount

KROK 6: Tworzenie widoków semantycznych

Plik SQL: sql/04_create_semantic_views.sql

  • Widoki (Warstwa Gold) oddzielają bazę od dashboardu w CREATE OR ALTER VIEW sem.[nazwa].
  • vw_sales_by_category buduje obliczenia procentowego wkładu tworząc małe CTE WITH totals AS (SELECT SUM(sale_dollars) AS all_sales ...).
  • Dzielenie sumy marży przez wolumen ma mechanizm przeciwko dzieleniu przez 0: NULLIF(SUM(bottles_sold), 0).
  • Skomplikowany SQL został wypchnięty z kodu Streamlit do serwera.

KROK 7: Kontrola Jakości (Quality Checks)

Plik SQL: sql/05_quality_checks.sql

  • eligible_staging_fact_row_count_difference: Test sprawdza czy ilość po filtrowaniu ze stagingu to ta sama ilość odesłana do Faktu. Ma wyjść absolutne 0 odchyleń.
  • null_foreign_keys: Zwraca ZERO, jeśli fakt bezpiecznie zmapował wszystkie wartości.
  • fact_dimension_join_failures: Robi LEFT JOIN pod każdą parę i zlicza wiersze osierocone. Wynik to oczywiście wymuszone: 0.
  • duplicate_[X]_numbers: Szuka takich samych numerków dla np. ID. Używa GROUP BY, jeśli posiada wynik HAVING COUNT(*) > 1, podnosi alarm.

Szybkie podsumowanie kroków (do prezentacji)

"Użyliśmy w pełni zdefiniowanego strumienia. Wymusiliśmy sprowadzanie na środowisko plików CSV (Extract), które poprzez model transformacji zapytań w warstwie operacyjnej SQL Server załadowane zostały do silnie odseparowanego warstwą pośrednią stagingu (Load/Stg), skąd odpowiednia logika deduplikacyjna załadowała poszczególne wymiary i ostatecznie złożyła do tablicy faktów (DW). Proces wieńczy kompilacja zestawu ustandaryzowanych biznesowo widoków połączona z absolutnymi i mierzalnymi wymogami jakości poprzez zbiór wywołań wertykalnych bazujących m.in. na teście Orphaned Keys."

SELECT 'eligible_staging_fact_row_count_difference' AS check_name,
       ABS(stg.row_count - fact.row_count) AS check_value
FROM (
    SELECT COUNT_BIG(*) AS row_count
    FROM stg.iowa_liquor_sales_raw
    WHERE COALESCE(sale_dollars, 0) >= 0
      AND COALESCE(bottles_sold, 0) >= 0
      AND COALESCE(volume_sold_liters, 0) >= 0
) stg
CROSS JOIN (
    SELECT COUNT_BIG(*) AS row_count FROM dw.fact_sales
) fact;

def add_daily_metrics(df: pd.DataFrame) -> pd.DataFrame:
    if "day_count" not in df.columns:
        return df

    result = df.copy()
    denominator = pd.to_numeric(result["day_count"], errors="coerce").astype(float)
    denominator = denominator.mask(denominator == 0)
    
    # Dynamiczne wyznaczanie wskaźników na podstawie dni w widoku
    result["avg_daily_sales"] = pd.to_numeric(result["total_sales"]) / denominator
    return result

def localize_figure(fig):
    def localize_axis(axis) -> None:
        current = axis.title.text
        if current in COLUMN_LABELS:
            axis.update(title_text=COLUMN_LABELS[current])

    fig.for_each_xaxis(localize_axis)
    fig.for_each_yaxis(localize_axis)
    return fig
