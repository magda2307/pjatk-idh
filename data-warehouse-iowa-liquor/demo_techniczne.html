Źródło danych

Publiczny rejestr hurtowej sprzedaży alkoholu stanu Iowa (Iowa Alcoholic Beverages Division). Każda dostawa do sklepu rejestrowana jako osobna linia faktury. Dane historyczne od 2012 r., ok. 2,7 mln wierszy rocznie.

Zmiana API - czerwiec 2026. Stan Iowa przeniósł portal z Socrata na Google Data Hub. Stare API zwraca 404. Nowe nie obsługuje paginacji ($limit, $offset, $where). Projekt obsługuje to automatycznie przez fallback na lokalny cache plików CSV - szczegóły w kroku 1.

Pipeline - 7 kroków

Kolejność wywołań w funkcji run_initial_etl() (src/run_initial_etl.py). Każdy krok to osobny task w Airflow. Przy błędzie konkretnego taska można go ponowić bez restartu całego DAG-u.

1. extract API Socrata → pliki CSV na dysku
2. create_sql_objects Skrypty SQL 00–03: CREATE DB / SCHEMA / TABLE
3. load_staging TRUNCATE + CSV → stg.iowa_liquor_sales_raw
4. load_dimensions DELETE + RESEED + stg → 6 tabel dw.dim_*
5. load_fact_sales DELETE + stg JOIN 6 dim → dw.fact_sales
6. semantic_views CREATE OR ALTER 16 widoków sem.*
7. quality_checks 14 zapytań SQL → Python → ValueError lub OK

Krok 1
Ekstrakcja

extract_iowa_liquor_sales() w src/extract/socrata_extract.py. Pobiera dane z Socrata API dla zakresu dat z konfiguracji (IOWA_START_DATE, IOWA_END_DATE). Wynik: lista plików CSV na dysku.

Ścieżka normalna - API działa

  1. Walidacja konfiguracji - format dat YYYY-MM-DD, start ≤ end, limit > 0. Błąd konfiguracji = ValueError przed jakimkolwiek requestem.
  2. Sesja HTTP z retry - 4 próby, backoff_factor=1.5 (opóźnienia: 0s, 1.5s, 3s, 6s), kody 429/500/502/503/504 automatycznie ponawiane.
  3. Paginacja - parametry: $where=date between '...' and '...', $limit, $offset, $order=date,invoice_line_no. Strony pobierane kolejno aż API zwróci 0 wierszy.
  4. Zapis atomowy - każda strona ląduje w katalogu tymczasowym data/raw/_extract_tmp/. Stare pliki kasowane dopiero po pomyślnym pobraniu wszystkich stron. Nazwy: iowa_liquor_sales_YYYY_part_NNN.csv.
  5. Manifest - plik data/processed/extract_manifest.json z listą plików, zakresem dat, liczbą wierszy i timestampem UTC. Krok 3 używa manifestu do znalezienia plików.

Ścieżka awaryjna - API niedostępne

  1. requests.RequestException złapany przez blok except.
  2. Katalog tymczasowy kasowany - brak niekompletnych plików.
  3. Funkcja write_cached_extract_from_raw_files() skanuje data/raw/ po plikach z poprzednich runów.
  4. Wiersze z tych plików filtrowane po kolumnie date do zadanego zakresu. Wyniki zapisywane do data/processed/fallback_raw/.
  5. Jeśli brak plików cache lub żaden wiersz nie pasuje do zakresu dat - FileNotFoundError i ETL się zatrzymuje.

Krok 2
Inicjalizacja SQL

create_sql_objects(). Wykonuje 4 skrypty SQL w kolejności. Wszystkie są idempotentne - sprawdzają istnienie obiektów przed tworzeniem, można uruchamiać wielokrotnie.

Skrypt 00

00_create_database.sql - wykonywany na bazie master (jedyne miejsce gdzie połączenie idzie do master, nie do docelowej bazy). Tworzy bazę IowaLiquorDW przez IF NOT EXISTS.

Skrypt 01

01_create_schemas.sql - tworzy 3 schematy przez IF NOT EXISTS: stg (Silver - oczyszczony staging po plikach Bronze na dysku), dw (Gold - model gwiazdy), sem (widoki semantyczne dla raportów).

Skrypt 02

02_create_staging_tables.sql - tworzy stg.iowa_liquor_sales_raw. Kolumny techniczne: staging_key BIGINT IDENTITY(1,1) PK, source_file NVARCHAR(260), load_timestamp DATETIME2 DEFAULT SYSUTCDATETIME(), source_row_hash CHAR(64), oraz wszystkie pola z CSV (klucze jako NVARCHAR, miary jako DECIMAL/INT).

Skrypt 03

03_create_dw_tables.sql - tworzy 7 tabel przez IF OBJECT_ID(...) IS NULL: dim_date (klucz INT YYYYMMDD, nie IDENTITY), dim_store, dim_product, dim_category, dim_vendor, dim_packaging (klucze IDENTITY), fact_sales (sales_key IDENTITY + 6 FK). FK definiowane na końcu skryptu przez ALTER TABLE ... ADD CONSTRAINT FOREIGN KEY.

Wynik: baza z kompletną strukturą tabel i kluczy obcych. Tabele puste - dane ładowane w krokach 3–5.

Krok 3
Staging

load_staging_from_raw_files() w src/load/sqlserver_loader.py. Czyści dane przez Pandas i ładuje do stg.iowa_liquor_sales_raw. Pierwsze działanie: TRUNCATE TABLE - staging zawsze zaczyna od zera.

Transformacje danych - po kolei

  1. Wczytanie CSV - pd.read_csv(dtype=str, keep_default_na=False). Wszystko jako string, bez automatycznego parsowania typów i bez zamiany wartości na NaN.
  2. Normalizacja nazw kolumn - lowercase, niealfanumeryczne → _, trim podkreśleń.
  3. Aliasy kolumn API - przemapowanie 10 nazw: invoice_line_no→invoice_and_item_number, store→store_number, name→store_name, zipcode→zip_code, vendor_no→vendor_number, itemno→item_number, im_desc→item_description, sale_bottles→bottles_sold, sale_liters→volume_sold_liters, sale_gallons→volume_sold_gallons.
  4. Parsowanie GPS - jeśli brak osobnych kolumn latitude/longitude, regex wyciąga je z POINT (lon lat). Wynik: dwie kolumny DECIMAL.
  5. Uzupełnienie brakujących kolumn - każda kolumna z listy STAGING_COLUMNS której nie ma w CSV → dodawana jako None.
  6. Row hash SHA-256 - hashlib.sha256("|".join(values).encode()).hexdigest() z 7 pól: invoice_and_item_number, date, store_number, item_number, sale_dollars, bottles_sold, source_file. Identyfikator wiersza do Change Data Capture.
  7. UPPERCASE dla kluczy biznesowych: invoice_and_item_number, store_number, county_number, category, vendor_number, item_number.
  8. Title Case dla nazw geograficznych: city, county.
  9. Normalizacja ogólnego tekstu - strip whitespace, wielokrotne spacje → jedna spacja, puste stringi → None dla: store_name, address, store_location, category_name, vendor_name, item_description, source_file.
  10. Kod pocztowy - regex wyciąga wszystkie cyfry, zwraca pierwsze 5. Jeśli mniej niż 5 cyfr - oryginalny tekst bez zmian.
  11. Wartości finansowe i numeryczne - strip $, strip ,, pd.to_numeric(errors='coerce'). Dla: state_bottle_cost, state_bottle_retail, sale_dollars, bottles_sold, pack, bottle_volume_ml, proof, volume_sold_liters, volume_sold_gallons, latitude, longitude.
  12. Data - pd.to_datetime(errors='coerce').dt.date. Nieparsowalne daty → None.
  13. Finalny NULL sweep - df.where(pd.notnull(df), None) - wszystkie NaN → Python None = SQL NULL.

BK - klucz biznesowy

Klucz z danych źródłowych (store_number, item_number, itp.). Używany do JOIN-ów przy ładowaniu i do identyfikacji w raportach. Nie jest FK - to zastępczy IDENTITY pełni rolę FK w fact_sales.

M - miara / W - wyliczona

M: wartość liczbowa z transakcji (bottles_sold, sale_dollars, itp.). W: kolumna wyliczona przy INSERT - nie pochodzi bezpośrednio ze źródła (margin_amount, volume_group, sales_line_count).

UNKNOWN - fallback key

Wymiary tekstowe mogą zawierać wiersz z kluczem biznesowym 'UNKNOWN'. Trafiają tam wiersze ze stagingu z NULL-owym lub pustym kluczem. Dzięki temu INNER JOIN w kroku 5 zachowuje takie rekordy po mapowaniu na znany klucz zastępczy.

Krok 4
Wymiary

load_dimensions(). Ładuje 6 tabel wymiarów ze stagingu. Full Refresh: przed ładowaniem - DELETE wszystkich faktów i wymiarów + DBCC CHECKIDENT RESEED 0 (reset IDENTITY).

Kolejność DELETE jest krytyczna. Najpierw DELETE FROM dw.fact_sales - bo fact_sales ma FK do wszystkich wymiarów. Potem DELETE na każdym wymiarze. Bez tej kolejności SQL Server odmawia usunięcia rekordów z wymiaru który ma powiązane fakty.
dim_date

Źródło: SELECT DISTINCT date FROM stg WHERE date IS NOT NULL

Co wyliczane przy INSERT:

  • date_key = CONVERT(INT, FORMAT(date, 'yyyyMMdd')) - np. 20230115. Klucz INT zamiast DATE umożliwia szybkie filtrowanie zakresów bez konwersji typów.
  • day, month, quarter, year, day_of_week - przez funkcje SQL DAY(), MONTH(), DATEPART().
  • day_name_en = DATENAME(weekday, date)
  • day_name_pl - CASE WHEN na DATENAME → polska nazwa dnia.
  • month_name_en = DATENAME(month, date)
  • month_name_pl - CASE WHEN na MONTH() → polska nazwa miesiąca.
  • is_weekend = 1 gdy Saturday lub Sunday, inaczej 0.
  • year_month = FORMAT(date, 'yyyy-MM') - string do grupowania w raportach.
dim_store
dim_product
dim_category
dim_vendor

Problem: tabela źródłowa jest transakcyjna - ten sam sklep (ten sam store_number) może mieć różne adresy w różnych transakcjach (błędy, zmiany w czasie). Do wymiaru musi trafić dokładnie 1 wiersz per klucz biznesowy.

Rozwiązanie - SCD Type 1 (overwrite, najnowszy stan):

warehouse_transform.py - dim_store (pattern identyczny dla dim_product/category/vendor)
WITH ranked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY
                COALESCE(NULLIF(store_number, ''), 'UNKNOWN')
            ORDER BY date DESC, staging_key DESC
        ) AS rn
    FROM stg.iowa_liquor_sales_raw
)
INSERT INTO dw.dim_store (
    store_number, store_name, address,
    city, zip_code, county, state_name,
    source_store_location, latitude, longitude
)
SELECT
    COALESCE(NULLIF(store_number, ''), 'UNKNOWN'),
    store_name, address, city, zip_code, county,
    'Iowa', store_location, latitude, longitude
FROM ranked
WHERE rn = 1;

ROW_NUMBER() OVER (PARTITION BY klucz ORDER BY date DESC) - rn=1 to wiersz z najpóźniejszą datą. Jeśli kilka wierszy ma tę samą datę - staging_key DESC jako tiebreaker. COALESCE(NULLIF(...,''),'UNKNOWN') - NULL i pusty string zamieniany na 'UNKNOWN' przed partycjonowaniem, więc te wiersze trafiają do jednej grupy (nie wiele grup NULL).

dim_packaging

Klucz naturalny: kombinacja (pack, bottle_volume_ml) - nie ma deduplikacji per jeden klucz tekstowy, bo opakowań nie "nadpisujesz". SELECT DISTINCT pack, bottle_volume_ml FROM stg + wyliczona kolumna:

warehouse_transform.py - volume_group (feature engineering)
CASE
    WHEN bottle_volume_ml = 0    THEN 'unknown'
    WHEN bottle_volume_ml < 500  THEN 'small'
    WHEN bottle_volume_ml < 1000 THEN 'standard'
    WHEN bottle_volume_ml < 1750 THEN 'large'
    ELSE                              'extra_large'
END AS volume_group

volume_group nie pochodzi ze źródła - wyliczana przy ładowaniu. Pozwala filtrować i grupować w raportach ("sprzedaż butelek small vs large") bez analizowania wartości liczbowych.

Wynik: 6 tabel wymiarów. Każdy klucz biznesowy dokładnie raz. Klucze zastępcze (IDENTITY) przydzielone od nowa po RESEED 0. Krok loguje liczbę wierszy w każdym wymiarze.

Krok 5
Tabela faktów

load_fact_sales(). Łączy staging z 6 wymiarami przez INNER JOIN i ładuje dw.fact_sales. Grain: jeden wiersz = jedna linia faktury (jeden SKU (Stock Keeping Unit - jednostka magazynowa), jeden sklep, jeden dzień).

INSERT - pełny SQL

warehouse_transform.py - load_fact_sales
-- Przed INSERT:
DELETE FROM dw.fact_sales;
DBCC CHECKIDENT ('dw.fact_sales', RESEED, 0);

INSERT INTO dw.fact_sales (
    date_key, store_key, product_key,
    category_key, vendor_key, packaging_key,
    invoice_number, source_row_hash,
    sales_line_count, bottles_sold, sale_dollars,
    volume_sold_liters, volume_sold_gallons,
    state_bottle_cost, state_bottle_retail,
    margin_amount
)
SELECT
    d.date_key,
    s.store_key,
    p.product_key,
    c.category_key,
    v.vendor_key,
    pk.packaging_key,
    raw.invoice_and_item_number,
    raw.source_row_hash,
    1 AS sales_line_count,
    COALESCE(raw.bottles_sold, 0),
    COALESCE(raw.sale_dollars, 0),
    COALESCE(raw.volume_sold_liters, 0),
    COALESCE(raw.volume_sold_gallons, 0),
    COALESCE(raw.state_bottle_cost, 0),
    COALESCE(raw.state_bottle_retail, 0),
    (COALESCE(raw.state_bottle_retail, 0)
      - COALESCE(raw.state_bottle_cost, 0))
        * COALESCE(raw.bottles_sold, 0) AS margin_amount
FROM stg.iowa_liquor_sales_raw raw
JOIN dw.dim_date d
    ON d.date = raw.date
JOIN dw.dim_store s
    ON s.store_number =
       COALESCE(NULLIF(raw.store_number,''),'UNKNOWN')
JOIN dw.dim_product p
    ON p.item_number =
       COALESCE(NULLIF(raw.item_number,''),'UNKNOWN')
JOIN dw.dim_category c
    ON c.category_number =
       COALESCE(NULLIF(raw.category,''),'UNKNOWN')
JOIN dw.dim_vendor v
    ON v.vendor_number =
       COALESCE(NULLIF(raw.vendor_number,''),'UNKNOWN')
JOIN dw.dim_packaging pk
    ON pk.pack = COALESCE(raw.pack, 0)
   AND pk.bottle_volume_ml =
       COALESCE(raw.bottle_volume_ml, 0)
WHERE COALESCE(raw.sale_dollars, 0) >= 0
  AND COALESCE(raw.bottles_sold, 0) >= 0
  AND COALESCE(raw.volume_sold_liters, 0) >= 0;

Decyzje projektowe

Marża wyliczana przy INSERT, nie po agregacji:
margin_amount = (retail - cost) × bottles_sold na poziomie wiersza. Gdyby liczyć marżę na zagregowanych danych (np. średnią cost × suma bottles), wynik byłby błędny matematycznie. Wyliczenie na ziarnku faktów i późniejszy SUM jest jedyną poprawną metodą.

sales_line_count = 1:
Stała wartość 1 w każdym wierszu faktów. Raporty mogą liczyć linie sprzedaży przez SUM(sales_line_count), a faktury osobno przez COUNT(DISTINCT invoice_number). Dzięki temu nie mieszają się dwie definicje: liczba linii faktury i liczba faktur.

INNER JOIN zamiast LEFT JOIN:
Do faktów trafiają tylko wiersze, które da się połączyć z kompletem wymiarów. To jest celowe - gwarantuje integralność referencyjną. NULL-owe albo puste klucze biznesowe są wcześniej mapowane przez COALESCE(NULLIF(...),'UNKNOWN'), więc nie są tracone tylko dlatego, że w źródle brakuje tekstowego identyfikatora.

Filtr ujemnych miar (WHERE ≥ 0):
Wiersze z ujemną sprzedażą (zwroty, korekty) są wykluczane z faktów. Liczba wykluczonych wierszy raportowana przez kontrolę jakości raw_negative_measure_rows_excluded_from_fact - widoczna w logach, nie powoduje błędu.

COALESCE na NULL-e w miarach:
COALESCE(bottles_sold, 0) itp. - NULL w mierze nie powoduje NULL w fakcie. Wiersz z nieznaną liczbą butelek trafia do faktów z wartością 0, a nie jest pomijany przez JOIN/WHERE.

Wynik: dw.fact_sales z pełnym zestawem miar i 6 kluczami obcymi. Zwracany COUNT(*) z tabeli faktów.

Widoki semantyczne

create_semantic_views() - skrypt sql/04_create_semantic_views.sql. Tworzy 16 widoków przez CREATE OR ALTER VIEW - jeśli istnieją, nadpisywane bez DROP. Streamlit odpytuje tylko sem.*, nie dw.*.

Dlaczego warstwa semantyczna? (1) Aplikacja dostaje gotowe, zagregowane dane - nie pisze JOIN-ów po 6 tabelach. (2) KPI i udziały % liczone w jednym miejscu - wszędzie ten sam wynik. (3) Dzielenie przez zero obsługiwane przez NULLIF - błąd SQL zamieniany na NULL. (4) Nowy raport = nowy widok, bez dotykania tabel.

Kontrole jakości

run_quality_checks() + validate_quality_check_results(). Skrypt sql/05_quality_checks.sql - 14 zapytań SELECT, każde zwraca parę (check_name, check_value). Python waliduje wszystkie wyniki naraz i zbiera błędy. Jeden ValueError z listą wszystkich nieudanych kontroli = Airflow task FAILED.
